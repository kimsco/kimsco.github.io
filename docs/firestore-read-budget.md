# Firestore 조회 점검 및 절감 검증

## 1.0.74: 단일 기기 우선, 다른 기기의 운동 기록은 수동 불러오기

1.0.73의 `recordUpdates` 변경 항목·확인 문서 쓰기와 자동 조회를 제거했습니다. 운동 세트 원본 저장은 다시 1쓰기이며 자동 달력/최근 운동일 처리 비용은 별도입니다. 이미 받은 기록과 과거 날짜 페이지는 계속 만료 없이 로컬에서 재사용합니다. 프로필·식단 등의 기존 갱신 정책은 유지합니다.

로그인한 사용자는 설정의 **운동 기록 다시 불러오기**를 눌러 서버의 전체 `records`·`accessoryRecords`를 수동 조회할 수 있습니다. 이 동작은 서버의 변경·삭제를 반영하며, 다운로드한 문서 수만큼 읽기가 발생합니다. 앱 시작·복귀·일반 홈 새로고침에서는 이 전체 조회를 수행하지 않습니다. 재설치 후 최초 조회와 아직 안 받은 과거 조회는 기존 정책을 유지합니다.

수동 조회 중 미전송·진행 중인 로컬 쓰기는 보존하며, 계정 변경·탈퇴 중에는 결과를 적용하지 않습니다. 두 서버 조회가 성공한 뒤 로컬 저장을 수행하고 이력 완료 표시를 남깁니다. 네트워크/저장 실패는 화면에 알리고 재시도할 수 있습니다. 게스트에게는 버튼을 표시하지 않습니다.

1.0.73에서 생성한 변경 문서는 이번 배포에서 대량 삭제하지 않습니다. 추가로 사용하지 않으며 회원 탈퇴 시 정리 대상에는 유지합니다. 1.0.73 구버전이 열린 기기는 해당 버전의 동작을 계속 수행할 수 있으므로 1.0.74로 갱신해야 새 정책이 적용됩니다.

## 1.0.73: 받은 운동 기록은 영구 로컬 재사용, 다른 기기는 변경 항목만 조회

- `records`·`accessoryRecords` 초기 최근 30일 조회의 성공 표시와 로컬 데이터가 있으면 시간이 지나도 해당 묶음을 다시 조회하지 않습니다. 기존 계정의 정상 초기 동기화 표시를 한 번 이관합니다. 실패한 조회는 완료 표시하지 않습니다.
- 과거 날짜 페이지 커서와 전체 이력 완료 표시는 24시간 만료를 제거했습니다. 그래프·루틴의 전체 이력 요청도 날짜 페이지 커서를 이어서 사용하므로 이미 받은 과거 페이지를 다시 읽지 않습니다. 아직 받지 않은 과거는 기존처럼 운동 날짜 4개 단위로 받습니다.
- 기기 저장 데이터 소실·손상은 재조회 대상입니다. 영구 보존은 브라우저가 저장 공간을 유지한다는 조건이며 앱 삭제·사이트 데이터 삭제·저장 공간 회수까지 막는다는 뜻이 아닙니다.
- 다른 기기의 변경은 `users/<uid>/meta/recordUpdates` 한 문서의 서버 시각을 확인합니다. 이전 커서와 같으면 원본 기록·변경 목록을 읽지 않습니다. 시작 시와 복귀 시 최대 5분 간격으로 확인하며, 홈 당겨서 새로고침은 즉시 확인합니다. 앱 재실행은 확인 문서 1읽기 등이 발생하므로 앱 전체 읽기 0을 뜻하지 않습니다.
- 추가·수정·삭제 시 원본 기록과 `recordUpdates/<outbox revision>` 변경 항목, 확인 문서를 **하나의 원자적 batch**로 저장합니다. 원본 세트 쓰기 외에 **변경 항목 1쓰기 + 확인 문서 1쓰기**가 추가됩니다. 삭제도 원본 삭제 외에 두 쓰기가 추가됩니다. 변경 항목은 별도 문서로 쌓이며 자동 만료시키지 않습니다. 오래 오프라인이었던 기기의 삭제 동기화도 보장하기 위한 비용입니다.
- 변경 항목에는 변경 당시 데이터/삭제 표시와 서버 시각이 있습니다. 커서 이후 항목만 페이지로 받아 기기 캐시에 반영합니다. 로컬 미전송 작업이 우선하며, 모든 페이지의 로컬 저장이 성공한 후에만 커서를 갱신합니다. 계정 변경·권한/네트워크 실패·저장 실패 시 진행을 중단하고 재시도할 수 있습니다.
- 깨끗한 설치는 초기 스냅샷 직전에 서버 변경 기준을 먼저 잡아 과거 변경 목록 전체를 다운로드하지 않습니다. 기존 캐시가 있는 기기는 새 피드 시작 이후 누락된 변경부터 반영합니다.
- 이 동기화에는 변경을 만드는 기기도 **1.0.73 이상**이어야 합니다. 구버전/콘솔에서 원본 문서만 직접 수정하면 변경 항목이 없어 자동 감지할 수 없습니다. 사용자 제공 규칙의 소유자 하위 경로 허용 범위 안에서 동작하며 운영 규칙을 여기서 변경하지 않았습니다. 새 쿼리는 단일 `at` 필드와 문서 ID 정렬을 사용하며 새 복합 색인을 요구하지 않습니다.
- 회원 탈퇴 시 새 변경 컬렉션도 삭제하고 계정 접두어의 커서를 정리합니다. 다른 사용자 데이터에는 접근하지 않습니다.

프로필·식단·루틴·달력·공지 등은 기존 정책을 유지합니다. 이번 변경은 세트 운동 기록의 반복 다운로드를 줄이는 작업입니다. 테스트는 격리된 Firebase 대역과 단위 테스트만 사용하며 운영 Firestore를 조회하지 않습니다.

## 1.0.30: 운동한 날짜 4개씩 서버 조회

최근 30일 초기 조회와 날짜별 화면 표시를 유지하고, 목록에서 더 과거가 필요할 때 기록이 있는 날짜 4개를 조회합니다. 날짜 탐색은 1문서 제한 쿼리로 하며, 그 날짜의 나머지 세트는 문서 ID 커서와 최대 100문서 내부 분할로 모두 받습니다. 날짜 탐색으로 받은 세트를 재사용하여 중복으로 읽지 않습니다. 다섯째 운동 날짜의 기록을 미리 읽지 않습니다. 따라서 사용자 화면의 페이지 단위는 4개 운동 날짜이며 50세트 제한은 제거했습니다. 날짜별 세트 수에 따라 읽기가 달라지고, 날짜 경계 탐색·빈 쿼리에는 최소 읽기 비용이 발생할 수 있습니다.

페이지 커서·조회 범위·완료 여부는 기존 계정 접두어의 `read_fresh:historyPage:<종류/종목>`에 저장합니다. 기록 캐시를 저장한 뒤에만 커서를 전진시킵니다. 재실행 시 실제 기록 배열과 24시간 이내 커서가 있으면 이어서 받습니다. 전체 이력의 24시간 캐시가 있으면 페이지 조회도 생략합니다. 네트워크·색인·저장 실패는 수동 재시도 버튼을 표시하며 전체 조회로 우회하지 않습니다. 추가 서버 문서·쓰기는 없습니다. 그래프·루틴의 전체 이력 요청은 기존 24시간 캐시로 유지합니다.

검증은 운동 날짜 9개, 총 159세트(한 날짜 123세트 포함)로 4일·4일·1일씩 누락·중복 없이 조회하고 재실행 후 커서 재사용을 확인합니다. 하루의 많은 세트도 분할된 내부 요청으로 받아 같은 화면 페이지에 포함하며 계정 변경·저장 실패가 커서를 전진시키지 않는 것을 검사합니다.

### 운영 배포 전 필수: 복합 색인 확인

`firestore.indexes.json`의 두 색인이 준비되어야 날짜순 제한 조회가 동작합니다. 기존 운영 색인 목록이 저장소에 없으므로 이 파일로 기존 전체 색인 설정을 덮어쓰지 않습니다. 운영 프로젝트에는 아래 두 색인을 추가하거나 같은 설정이 이미 있는지 확인해야 합니다.

| 컬렉션 | 쿼리 범위 | 필드 |
| --- | --- | --- |
| records | 컬렉션 | lift 오름차순, date 내림차순, __name__ 내림차순 |
| accessoryRecords | 컬렉션 | exercise 오름차순, date 내림차순, __name__ 내림차순 |

Firebase 콘솔에서는 마지막 `__name__`가 최종 정렬 방향인 내림차순으로 자동 추가될 수 있습니다. 사용자는 Firebase 콘솔에서 두 색인 생성 완료를 확인했습니다. 이 확인을 근거로 머지·배포합니다. 운영 인증정보가 없어 실제 프로젝트의 색인 생성·조회는 여기서 수행하지 않았습니다. 검증은 격리된 데이터와 SDK 대역을 사용했습니다.

## 1.0.29: 과거 전체 이력 캐시를 재실행 후에도 재사용

`liftHistory:<lift>`와 `exerciseHistory:<name>` 성공 시각을 기존 `mf_account_v2:<uid>:read_fresh:<key>`에 저장하고, 해당 기록 배열이 로컬에 있는 경우 24시간 재사용합니다. 기본 종목 목록·최근 보조운동 캐시는 5분, 기존 초기 전체 동기화는 1시간을 유지합니다. 신규 컬렉션·변경 피드·서버 쓰기는 추가하지 않습니다.

전체 이력 조회 후 실제 기록 캐시 저장이 성공해야 조회 완료 플래그와 성공 시각을 설정합니다. 빈 결과도 배열을 저장합니다. 저장 실패는 완료 처리하지 않고 다음 요청에서 재시도합니다. 로컬 배열이 없거나 JSON이 손상되었거나 시각이 미래이면 캐시를 신뢰하지 않습니다. 회원 탈퇴의 계정 접두어 삭제에 성공 시각이 포함됩니다.

24시간 만료 후 전체 이력을 요청하면 서버의 수정·삭제까지 로컬 이력에 반영하며, 조회 중 새로 저장한 로컬 기록과 미전송 작업은 보존합니다. 이 기기의 저장·삭제는 기존 로컬/outbox 흐름을 유지합니다. 다른 기기의 과거 변경은 유효한 캐시 동안 즉시 반영되지 않습니다. 과거 목록의 화면상 날짜 단위 표시와 서버 전체 이력 쿼리는 이번 변경에서 유지되므로 최초 전체 조회·24시간 만료 후 재조회 비용은 그대로 남습니다. 실제 서버 페이지 조회는 별도 작업입니다.

검증: `tests/history-cache-smoke.py`는 격리된 데이터로 재실행 후 조회 재사용, 24시간 만료 후 원격 수정·삭제, 로컬 저장 실패 후 재시도, 로컬 캐시 소실 후 재조회를 확인합니다.

## 1.0.28: 1.0.27 변경 문서 동기화 철회

`recordChanges`와 `meta/recordSync`를 사용하는 저장·조회·버전 확인을 제거하고 1.0.26의 계정별 캐시 및 기존 durable outbox를 복원했습니다. 이후 새 세트는 기록 문서에 직접 반영되며 변경 피드 문서를 추가하지 않습니다. 기존 오프라인 재시도·중복 방지와 5분 종목/최근 보조운동 캐시는 유지합니다. 달력·마지막 운동 요약 등 기존 저장 과정의 별도 읽기·쓰기는 계속 발생하므로 저장 전체 비용이 쓰기 1건만이라고 보장하지 않습니다.

이미 저장된 운동 기록과 변경 문서를 운영 서버에서 삭제하지 않았습니다. 이전 변경 문서는 이 버전에서 조회하지 않으며, 회원 탈퇴 시 잔여 데이터가 누락되지 않도록 `recordChanges` 삭제 대상은 유지합니다. `meta/recordSync`는 기존 `meta` 삭제 대상에 포함됩니다. 아직 1.0.27을 실행하는 다른 기기는 업데이트 전까지 변경 문서를 사용할 수 있습니다.

`loadRecordsFromFirestore`의 전체 기록 조회 함수는 현재 정의만 있고 앱 흐름에서 호출하지 않습니다. 이 함수의 코드가 있다는 이유로 실제 사용량 원인이라고 계산하지 않습니다.

## 측정 결과

`tests/read-budget-smoke.py`의 격리된 fixture에서 최근 보조운동 기록 100개를 두고 홈↔기록, 가슴↔등을 10회 왕복했습니다. 수정 후 최근 보조운동 조회는 최초 1회·100문서 반환으로 유지됐습니다. 이전 탭 핸들러는 같은 상황에서 초기 100 + 재진입 1,000 = 1,100문서를 반환할 수 있으므로, 이 조회 경로의 반복 읽기 약 91%를 줄입니다. 이는 테스트 시나리오 결과이며 운영 전체 비용이 91% 줄었다는 뜻이 아닙니다.

5분 만료 후 서버 종목 수정과 최근 기록 삭제를 반영하며, 짧은 재실행 후 기록/가슴 재진입은 해당 쿼리가 0회였습니다. 재실행 시 로컬 캐시가 없거나 시계가 뒤로 바뀌어 저장 시각이 미래가 되면 신선도를 신뢰하지 않습니다. 실패한 요청은 신선하게 저장하지 않습니다. 저장 시각은 `mf_account_v2:<uid>:read_fresh:<resource>`이고 계정 삭제의 기존 접두어 정리에 포함됩니다.

`readCache.report()`는 페이지 메모리에만 집계합니다. 시작·재사용·동시 요청 합치기·실패 횟수와 privateSnapshot 경로의 원본 반환 문서 수/추정 서버 읽기를 제공하며 사용자 데이터나 식별자는 포함하지 않습니다. Firestore 콘솔 수치와 정확히 같은 청구 계측이 아닙니다. 보안 규칙의 추가 읽기, 인덱스 엔트리 읽기, 공개 실시간 구독, 서비스 내부 트랜잭션/요약 조회 등은 이 숫자에 완전히 포함되지 않습니다. 설정 진단 UI나 원격 로그를 추가하지 않습니다.

## 갱신과 정확성

내 저장·수정·삭제는 로컬 데이터와 기존 durable outbox를 사용하므로 서버 전체 재조회 없이 화면에 즉시 반영합니다. 최신 캐시 재사용 시 이전 서버 응답을 다시 덮어쓰지 않습니다. 다른 기기의 최근 보조운동/종목 변경은 마지막 성공 조회로부터 5분이 지난 뒤 해당 화면 재진입·부위 선택·앱 focus/온라인 복귀 때 재조회합니다. 계속 가만히 있는 동안 매 5분 폴링하지 않습니다.

최근 보조운동 조회 범위 내에서 서버에 없는 기록은 제거하되, 이전 기간 기록·레거시 로컬 기록·현재 미전송 overlay·조회가 시작된 뒤 새로 저장된 로컬 기록을 보존합니다. 다른 계정의 응답은 반영하지 않습니다. Firebase 원본 운영 데이터를 읽거나 삭제하여 테스트하지 않습니다.

## 남는 비용과 배포 후 관찰

과거 전체 기록 조회와 운동도감 최초 전체 스냅샷은 여전히 문서 수에 비례합니다. 이를 변경하려면 그래프/최고기록의 완전성을 유지하는 요약 또는 별도의 페이지 조회가 필요합니다. 이 배포에서 기존 기록을 임의 개수로 잘라 정확성을 훼손하지 않습니다.

실제 Firebase 하루 사용량은 다른 사용자·콘솔·재설치·최초 이관·집계 지연 영향을 받습니다. 1.0.26에서 비슷한 일반 사용 조건의 하루 사용량을 비교해야 전체 절감률을 판단할 수 있습니다. 무료 한도 초과 방지를 보장하지 않습니다.
